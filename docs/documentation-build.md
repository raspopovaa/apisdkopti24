# Как собирается документация

Документация SDK строится из исходников, а не пишется вручную целиком. Справочник
методов и моделей генерируется из каталога операций, метаданных и сигнатур кода,
поэтому он не расходится с тем, что делает библиотека. Руководства (установка,
конфигурация, ошибки, безопасность) написаны вручную и лежат рядом.

## Что и чем собирается

| Шаг | Инструмент | Что делает |
|---|---|---|
| Генерация | `scripts/generate_docs.py` (логика в `scripts/documentation_generator.py`) | Пишет Markdown справочника в `docs/methods/`, `docs/data-types/`, `docs/reference/` |
| Источники генерации | `specifications/operation-catalog.json`, `specifications/documentation.yaml`, публичные сервисы и Pydantic-модели | Операции, ограничения, описания доменов, поля моделей |
| Примеры | `scripts/generate_method_examples.py` | Учебные примеры в `examples/methods/` и `docs/examples/` |
| Сайт | MkDocs с темой Material (`mkdocs.yml`) | Собирает HTML из `docs/`: русский язык, поиск, навигация |
| Версии | mike | Публикует документацию по линиям `major.minor` в ветку `gh-pages`, `latest` указывает на текущую |
| Хостинг | GitHub Pages | Отдаёт содержимое `gh-pages` |

Сгенерированные страницы руками не правятся. Чтобы изменить текст в справочнике,
меняют каталог операций, `specifications/documentation.yaml` или генератор и
запускают генерацию заново.

## Что проверяет CI

Workflow `Docs` запускается на каждом pull request, `Pages` публикует сайт при
push в `main`. Оба выполняют одни и те же проверки:

1. `python scripts/generate_docs.py` перегенерирует `docs/`.
2. `git diff --exit-code -- docs/` падает, если результат отличается от
   закоммиченного. Так документация не отстаёт от кода.
3. `pytest tests/test_documentation_generator.py` проверяет контракты генератора.
4. `mkdocs build --strict` собирает сайт. Битая ссылка или страница вне навигации
   роняют сборку.
5. Только в `Pages`: `mike deploy` публикует версию, затем скрипт проверяет, что
   в опубликованных страницах есть ожидаемые фрагменты.

## Как собрать документацию локально

GitHub для этого не нужен: все инструменты входят в зависимости проекта.

```bash
uv sync --all-extras
uv run make docs
uv run mkdocs serve
```

`uv run make docs` выполняет генерацию и `mkdocs build --strict`: это те же шаги, что
упадут в CI. `mkdocs serve` поднимает сайт на `http://127.0.0.1:8000` и
перестраивает его при сохранении файла. Перед коммитом запускайте `uv run make docs` и
добавляйте в коммит изменившиеся файлы из `docs/`.

Просмотр версий без публикации:

```bash
uv run mike list
uv run mike serve
```

Команды `mike deploy` и `mike set-default` выполняет только GitHub Actions: они
записывают в `gh-pages`. Подробности о версиях и публикации: [Версии и
совместимость](versioning.md).

## Можно ли обойтись без GitHub

Да. Генератор и MkDocs работают локально и не зависят от GitHub. Сайт собирается в
каталог `site/` командой `uv run mkdocs build --strict`. Его можно положить на
любой веб-сервер, во внутренний портал или открыть как набор HTML-файлов. От
GitHub зависят только автоматическая проверка на pull request и публикация
версий через `gh-pages`. Вместо них подходит любая другая система CI, которая
выполняет те же пять шагов.
