# Ручная проверка 89 методов

Сценарий `examples/check_all_89_real_api.py` последовательно проводит оператора через
все зарегистрированные методы SDK. Он предназначен для контролируемой проверки на
выбранном API-окружении и не запускает мутации без явного подтверждения.

## Запуск

Подготовьте локальный `.env.integration`, который не должен попадать в Git, затем
запустите:

```bash
python examples/check_all_89_real_api.py --env-file .env.integration
```

Для каждого метода сценарий показывает:

1. назначение метода, путь сервиса и доступные ранее найденные идентификаторы;
2. HTTP-метод, версию, endpoint и расположение параметров по спецификации;
3. безопасный пример исходящего запроса с фиктивными идентификаторами;
4. Pydantic DTO запроса либо сообщение о проверке параметров сигнатурой метода;
5. приглашение ввести обязательные и необязательные значения;
6. фактический очищенный wire-запрос;
7. HTTP-ответ, схему Pydantic-модели ответа и валидированные данные.

Значения API key, session ID, договоров, карт, пользователей и других идентификаторов
маскируются при выводе HTTP-данных. Не публикуйте полный вывод терминала: бизнес-поля
ответа могут содержать конфиденциальные сведения, которые невозможно определить
только по имени поля.

## Управление выполнением

Для читающего метода нажмите Enter, чтобы выполнить запрос, `e`, чтобы заново ввести
параметры, или `s`, чтобы пропустить метод. Для мутации Enter недостаточно: сценарий
принимает только явное `yes`/`да` и повторно предупреждает о возможном изменении
данных или тарификации.

Перед мутацией заранее подготовьте план восстановления. Создавайте только временные
объекты с узнаваемым уникальным именем и сразу проверяйте соответствующий метод
удаления. Не подтверждайте денежные операции, блокировку карт, PIN/MPC и выпуск карт
на рабочем договоре без отдельного согласования.

## Интерпретация результата

`OK` означает, что сервер принял запрос и ответ прошёл текущую Pydantic-валидацию.
Это подтверждает только фактически использованный вариант данных. `ERROR` необходимо
сопоставить с напечатанным wire-запросом, HTTP-кодом и таблицей спецификации. Один
успешный ответ не подтверждает все optional-поля и не переводит provisional-контракт
в verified автоматически.
