# Ручная проверка 89 методов

Сценарий `examples/check_all_89_real_api.py` последовательно проводит оператора через
все зарегистрированные методы SDK. Он предназначен для контролируемой проверки на
выбранном API-окружении и не запускает мутации без явного подтверждения.

## Запуск

Подготовьте локальный `.env.integration`, который не должен попадать в Git, затем
запустите:

```bash
python examples/check_all_89_real_api.py --env-file .env.integration
```

Для каждого метода сценарий показывает:

1. назначение метода, путь сервиса и доступные ранее найденные идентификаторы;
2. HTTP-метод, версию, endpoint и расположение параметров по спецификации;
3. безопасный пример исходящего запроса с фиктивными идентификаторами;
4. Pydantic DTO запроса либо сообщение о проверке параметров сигнатурой метода;
5. приглашение ввести обязательные и необязательные значения;
6. фактический очищенный wire-запрос;
7. HTTP-ответ, схему Pydantic-модели ответа и валидированные данные.

При выводе HTTP-данных скрываются только секреты: API key, session ID, логин, пароль,
PIN, токены, `device_id`, платёжные данные QR, а в запросах также SMS-код (`code`).
ID договоров, карт и пользователей, даты и коды статусов видны, чтобы их можно было
сверить и подставить в следующие запросы. Журналы SDK (`LOGGER_FILE`,
`REQUEST_LOG_FILE`) по-прежнему очищаются полностью. Не публикуйте вывод терминала и
файлы ответов: в них есть договорные и персональные данные.

## Сохранение ответов

Временная диагностическая функция: каждый HTTP-ответ записывается в
`responses-<дата-время>.jsonl` в каталоге основного журнала SDK (`LOGGER_FILE`
из `.env`, по умолчанию `./api.log`). Рядом сохраняется `*.known.json` со
значениями, запомненными для следующих запросов. Скрываются только секреты
(`session_id`, пароль, PIN, токены, `api_key`), идентификаторы остаются. Файлы
создаются с правами `0600`.

Каждая запись содержит пояснения:

- `operation` и `operation_description` — метод SDK и что он делает;
- `input_parameters` — параметры, введённые или подставленные для метода:
  имя, значение и описание;
- `request` и `response` — отправленный запрос без заголовков и полный ответ;
- `field_descriptions` — описание каждого поля запроса и ответа по пути вида
  `data.result[].card_id`.

Описания берутся из Pydantic-моделей SDK и из `specifications/documentation.yaml`
и `specifications/parameter-descriptions-1.1.60.yaml`. Для описаний из
спецификаций нужен установленный PyYAML; без него остаются только описания моделей.

`--responses-file PATH` задаёт другой файл, `--no-save-responses` отключает запись.

## Повтор с параметрами прошлого прогона

`--from-responses PATH` читает `responses-*.jsonl` прошлого прогона. Введённые тогда
параметры каждого метода становятся его значениями по умолчанию, ID из ответов
(договор, карта, пользователь, шаблон и т. п.) запоминаются, а список АЗС и
справочники берутся из файла без повторной загрузки. Скрытые значения (`***`) не
подставляются, повреждённые строки пропускаются.

Автоматический режим `examples/check_all_89_auto.py` не задаёт вопросов о
параметрах, для которых значение известно, а необязательные параметры без значения
оставляет пустыми. Читающие методы выполняются сразу, изменяющие по умолчанию
требуют подтверждения:

```bash
python examples/check_all_89_auto.py --env-file .env.integration \
    --from-responses responses-20260925-223926.jsonl
```

- `--mutations skip` пропускает методы, изменяющие данные или тарифицируемые;
- `--no-prompt` пропускает метод, если для обязательного параметра нет значения;
- остальные параметры передаются `check_all_89_real_api.py`.

## Управление выполнением

Для читающего метода нажмите Enter, чтобы выполнить запрос, `e`, чтобы заново ввести
параметры, или `s`, чтобы пропустить метод. Для мутации Enter недостаточно: сценарий
принимает только явное `yes`/`да` и повторно предупреждает о возможном изменении
данных или тарификации.

Перед мутацией заранее подготовьте план восстановления. Создавайте только временные
объекты с узнаваемым уникальным именем и сразу проверяйте соответствующий метод
удаления. Не подтверждайте денежные операции, блокировку карт, PIN/MPC и выпуск карт
на рабочем договоре без отдельного согласования.

## Интерпретация результата

`OK` означает, что сервер принял запрос и ответ прошёл текущую Pydantic-валидацию.
Это подтверждает только фактически использованный вариант данных. `ERROR` необходимо
сопоставить с напечатанным wire-запросом, HTTP-кодом и таблицей спецификации. Один
успешный ответ не подтверждает все optional-поля и не переводит provisional-контракт
в verified автоматически.
