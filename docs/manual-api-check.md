# Ручная проверка методов на реальном API

В `tools/live_check/` лежит по одному скрипту на каждый из 89 методов SDK. Скрипт
вызывает один метод на выбранном API-окружении, показывает фактический HTTP-запрос
и ответ, проверяет ответ моделью SDK и сохраняет результат. Инструмент нужен, чтобы
сверить SDK с реальным API. Чтобы научиться пользоваться методами, откройте
[учебные примеры](examples/index.md).

## Подготовка

1. Скопируйте `tools/live_check/test_data.example.json` в
   `tools/live_check/test_data.json` и заполните:
   - `common` — общие данные: договор, карта, пользователь, шаблон, период;
   - `methods` — данные конкретных методов: тела запросов, суммы, коды из SMS;
   - `overrides` — замена любых параметров вызова конкретного метода.

   Значения в угловых скобках — заглушки: метод, которому они нужны, не запустится
   и подскажет, что заполнить. `test_data.json` в git не попадает.
2. Положите `.env` с `API_BASE_URL`, `API_KEY`, `API_LOGIN` и `API_PASSWORD` в
   `tools/live_check/` или в корень репозитория либо укажите путь в
   `APISDK_ENV_FILE`.
3. Установите SDK из репозитория: `pip install -e . pyyaml`.

## Запуск

```bash
python tools/live_check/get_cards_v2.py
```

Перед вызовом скрипт авторизуется с `common.contract_id`, после вызова выходит из
сессии. В начале каждого файла описано, что делает метод, какой HTTP-запрос он
отправляет, какие параметры и модели использует и какие ошибки возможны.

Файлы методов создаёт `tools/live_check/_generate.py`, а CI проверяет, что они
совпадают с выводом генератора. Поэтому значения меняйте в `test_data.json`, а не
в файлах методов.

## Результат

Итог выводится одной строкой:

- `УСПЕХ` — ответ прошёл проверку модели SDK;
- `ОШИБКА МОДЕЛИ` — HTTP-ответ получен, но не совпал с моделью: выводятся поле,
  тип ошибки и значение;
- `ОШИБКА` — ошибка API с кодом и сообщением сервера, сетевая ошибка или локальная
  проверка SDK.

Файл `tools/live_check/results/<метод>-<дата-время>.json` содержит параметры,
запрос, полный ответ, итог и несовпавшие поля. Файлы создаются с правами `0600`.
Скрываются только секреты: API key, session ID, логин, пароль, PIN, SMS-код,
`device_id`, платёжные данные QR и `card_number`. ID договоров, карт и
пользователей видны, чтобы их можно было подставить в следующие запросы. Папка
`results/` в git не попадает; не публикуйте её содержимое и вывод терминала — в них
есть договорные и персональные данные.

## Изменяющие методы

Методы, которые изменяют данные или тарифицируются, запрашивают подтверждение:
нужно ввести `yes`. Перед такой проверкой подготовьте план восстановления.
Создавайте только временные объекты с узнаваемым именем и сразу проверяйте метод
удаления. Не подтверждайте денежные операции, блокировку карт, PIN/MPC и выпуск
карт на рабочем договоре без отдельного согласования.

## Как понимать результат

`УСПЕХ` означает, что сервер принял запрос и ответ прошёл текущую проверку
Pydantic. Это подтверждает только фактически использованный вариант данных.
`ОШИБКА` сопоставьте с показанным HTTP-запросом, кодом ответа и спецификацией. Один
успешный ответ не подтверждает все необязательные поля и не переводит
provisional-контракт в verified автоматически.
