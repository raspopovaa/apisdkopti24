# Repository guidance for Codex

## Project context

- This repository contains `apisdkopti24`, an asynchronous Python SDK for a
  corporate fuel-card API.
- Supported Python versions are 3.11 through 3.14.
- Runtime code lives in `src/apisdkopti24/`.
- Tests live in `tests/`.
- User documentation lives in `README.md` and `docs/` and is built with MkDocs
  Material.
- API contracts and sanitized specification data live in `specifications/`.
- Public API documentation is generated by scripts in `scripts/`. Do not edit a
  generated page when the generator or its source metadata should change instead.

## Authoritative API sources

- Treat the following committed, sanitized sources as the authority for API
  behavior and documentation:
  - `specifications/api-contract-v1.1.60.yaml` for the corporate-client API
    contract version 1.1.60;
  - `specifications/api-qr-contract-v1.0.4.yaml` for the QR/MPC API contract
    version 1.0.4;
  - `specifications/api-methods.yaml` for method availability, billing, HTTP
    method, route, and external method identity;
  - `specifications/parameter-descriptions-1.1.60.yaml` for parameter semantics;
  - `specifications/documentation.yaml` for generated documentation metadata;
  - sanitized originals under `docs/specifications/` for context that cannot be
    represented completely in YAML.
- The source set originates from the corporate-client specification 1.1.60, QR
  specification 1.0.4, API response-code reference, API access instructions dated
  2026-04-08, and the comparative API-method matrix dated 2025-07.
- Read the relevant specification section before changing an endpoint, public
  signature, model field, alias, required/optional marker, enum, response envelope,
  billing flag, DEMO flag, timeout, or example.
- Keep provenance explicit. When two source documents disagree, do not silently
  choose one. Record the exact conflict, prefer the newer and more specific
  versioned contract only when that precedence is defensible, and ask for a
  decision if public behavior would change.
- Never copy raw credentials, API keys, session IDs, phone numbers, email addresses,
  contract identifiers, card numbers, or personal names from source examples into
  code, tests, generated contracts, fixtures, logs, or documentation. Preserve only
  sanitized structure and semantics.

## Working agreement

- Inspect the relevant implementation, tests, documentation, and `git status`
  before editing.
- Preserve existing user changes. Do not overwrite, revert, or reformat unrelated
  files.
- Make the smallest coherent change that fully solves the requested problem.
- Do not perform unrelated refactoring or introduce speculative abstractions.
- Do not invent API behavior, endpoint metadata, parameters, response fields, or
  compatibility claims. Verify them against source code, tests, and specifications.
- If requirements conflict with an external API contract, report the conflict
  before changing public behavior.

## Python code quality

- Use explicit type annotations for public and internal functions. Keep strict
  mypy compatibility.
- Prefer small functions and classes with one clear responsibility.
- Prefer composition and explicit dependencies over inheritance, hidden globals,
  and service locators.
- Use descriptive domain names. Avoid vague names such as `data`, `item`, `obj`,
  `foo`, or `helper` when a more precise name is available.
- Keep asynchronous paths non-blocking. Do not call blocking I/O from async code.
- Keep imports at module level unless a local import prevents an actual cycle or
  defers an optional dependency.
- Avoid broad `except Exception` handlers. When a boundary must catch an unknown
  exception, preserve its cause and convert it to a documented domain error.
- Preserve exception chaining with `raise ... from exc`.
- Add comments only when they explain a non-obvious decision, invariant, or API
  constraint. Do not narrate straightforward code.
- Keep public docstrings focused on behavior, parameters, return values,
  exceptions, and safety constraints.

## Public API and compatibility

- Treat exports from `apisdkopti24`, service attributes, public method
  signatures, request and response models, aliases, endpoint names, and wire-format
  fields as compatibility surfaces.
- Do not remove or rename a public symbol without explicit authorization and a
  documented migration path.
- Preserve wire-format field names even when Python naming conventions differ.
- Pass public method arguments by keyword in examples and new call sites.
- Keep endpoint declarations centralized in the runtime registry. Do not duplicate
  route, retry, timeout, billing, or DEMO metadata in service implementations.
- Validate contract changes with the scripts under `scripts/` and the independent
  YAML contracts under `specifications/`.

## Async lifecycle and reliability

- Prefer `APIClient` as an asynchronous context manager and reuse one client for
  the application lifecycle.
- Keep credentials isolated behind credential and API-key providers.
- Preserve the shared operation deadline and total-attempt budget across retries,
  rate limiting, and session recovery.
- Retry only operations explicitly marked safe and idempotent by endpoint policy.
- Never automatically repeat a mutating operation after an ambiguous network
  result.
- Preserve single-flight session recovery and avoid recursive session-lock
  acquisition.
- Some API operations may take longer than the nominal 120-second processing time
  because of database architecture and result size. Assign timeout classes from the
  specification and expected workload; do not apply one short timeout globally.
- Treat `409 duplicateConflict` as evidence of duplicate concurrent requests, not
  as a success response or an unconditional retry signal.
- Treat redirects explicitly. Do not silently send credentials or session headers
  to a different origin.

## API environments and access

- Keep the corporate-client API and QR API environment matrices distinct:
  - the corporate-client API is available on DEMO and production, but not on the QR
    test environment;
  - the QR API is available on its test and production environments, but not on
    DEMO.
- DEMO is shared, isolated from production systems, contains only a limited method
  set, is not billed, and returns simplified deterministic success/error behavior.
  Never present DEMO as proof that production data or every production method is
  available.
- The QR test environment is intended for QR integration testing, is populated with
  client-specific test data, is not billed, and may be unstable. Keep its base URL,
  credentials, and data separate from production.
- Production access, roles, object visibility, IP restrictions, quotas, and tariffs
  are server-side concerns. The SDK must expose clear errors and documentation but
  must not attempt to bypass them.
- API access requires an eligible fuel contract and an API-enabled account. API
  tokens are available only to accounts with the Administrator or Read role; only
  Administrator accounts can manage the API area and tokens in the customer portal.
- Token rotation invalidates the previous access path. Document rotation as a
  credential-management event and never cache a resolved token indefinitely.

## Billing and rate limits

- One API method call consumes one request for tariff accounting unless the
  method-level contract explicitly marks the operation as non-billable.
- Billing is method-specific. Never infer billing from the HTTP method, read/write
  semantics, service group, or method name. Use `specifications/api-methods.yaml`.
- Preserve documented exceptions, including non-billable invitation deletion and
  invitation creation without sending when the method contract marks them so.
- A free 500-request package may apply under the current service terms. Do not
  hardcode this commercial rule into SDK behavior; describe it as tariff-dependent
  documentation and direct users to verify the active package in the API portal.
- Apply the documented proactive client limits for the selected environment (the
  current specification identifies 2 requests/second for DEMO and 5 requests/second
  for production), while making the value configurable because contracts and
  special terms may override it.
- Client-side limiting does not replace server quotas or billing. Retries and
  re-authentication may consume additional server requests, so documentation must
  explain their effect instead of describing one business operation as necessarily
  one billable request.

## Response and error semantics

- Validate both the HTTP status and the JSON envelope status. A successful
  `status.code` must not mask an unsuccessful HTTP response, and a 2xx HTTP status
  must not mask an API-level error.
- Preserve the common response envelope fields `status`, `data`, and `timestamp`.
  Models must tolerate only the documented variants and must not invent missing
  success data.
- Map and document at least these contract error classes:
  - `400 validationFailed`: invalid request structure or parameter values;
  - `401 notAuthenticated`: missing, expired, or invalid session authorization;
  - `403 accessDenied`: role, API key, IP, quota/tariff, contract binding, or object
    ownership restriction;
  - `404 notFound`: route or requested object does not exist;
  - `409 duplicateConflict`: duplicate or simultaneous equivalent request;
  - `5xx`: temporary server, maintenance, or network-side failure.
- Re-authentication is appropriate only for an authenticated endpoint and a genuine
  `notAuthenticated` condition. Do not re-authenticate on `accessDenied`, quota
  exhaustion, invalid API key, or arbitrary 4xx responses.
- A generic recommendation to retry a 5xx response does not override endpoint
  idempotency. Automatic retries remain forbidden for unsafe mutations after an
  ambiguous result.

## QR and mobile card profile rules

- Treat the mobile card profile (MPC) and payment code as security-sensitive data.
  Never log the payment payload, PIN, SMS confirmation code, MPC security material,
  card number, device identifier, or raw QR response.
- A generated QR payment code has a limited lifetime, documented as up to 10
  minutes. Always expose and document the server-provided expiry and require callers
  to check it before presenting or reusing a code.
- Do not cache or reuse an expired payment code. Generate a new code after expiry.
- Respect the server counters such as `tries` and `transaction_count`; do not reset,
  reinterpret, or synthesize them client-side.
- Issuing an MPC requires SMS confirmation. An incorrect confirmation code may
  block MPC issuance; invalid payment security values may block payment for the
  card. Document the administrative reset operation and do not retry confirmation
  or payment blindly.
- Use the MPC update operation when the specification requires security material or
  PIN-related state to be refreshed. Deletion and reset operations are mutations and
  must follow the endpoint's explicit idempotency and billing metadata.
- Keep QR/MPC operations tied to the QR 1.0.4 contract. Do not infer missing QR
  behavior from the corporate-client 1.1.60 contract or from the comparison matrix.

## Security and privacy

- Never commit or print real API keys, passwords, session IDs, personal data,
  production credentials, or unsanitized specification examples.
- Never put credentials in `ConnectionSettings`, domain services, exception text,
  telemetry, or request audit logs.
- Do not log raw request or response payloads, URLs containing identifiers, or
  `APIError.context.raw_payload` without explicit sanitization.
- Require HTTPS for remote API endpoints. Do not weaken transport validation to
  make an example or test pass.
- Use placeholders such as `api.example.ru`, `contract-id`, and `card-id` in tests
  and documentation.

## Tests

- Add or update focused tests for every behavior change.
- A bug fix must include a regression test that fails for the original behavior.
- Cover success, validation failure, API failure, timeout, cancellation, and
  concurrency behavior when relevant.
- Do not weaken, skip, or delete a test merely to make the suite pass.
- Prefer deterministic tests with injected clocks and transports. Do not access a
  real API unless the user explicitly requests an integration test.
- Run the narrowest relevant test first, followed by the complete quality gate when
  practical.

## Documentation

- Update `README.md` and the relevant files in `docs/` whenever public behavior,
  installation, configuration, errors, or compatibility changes.
- Write user-facing documentation in Russian unless the surrounding document uses
  another language.
- Use active voice, concise paragraphs, task-oriented headings, and consistent
  terminology.
- Make examples complete, copy-pasteable, asynchronous where required, and
  compatible with the current public API.
- Explain safety, billing, DEMO availability, retry, and contract-selection
  constraints next to the affected operation.
- Keep internal links descriptive and valid. Add a next-step link to substantial
  guide pages when it helps the reader continue.
- Never include real credentials, personal data, production URLs, or secrets in
  documentation.
- After changing public services, models, or endpoint metadata, regenerate the API
  documentation before editing generated output manually.
- For every documented method, include material operational constraints from the
  source specification: required headers and contract context, environment
  availability, billing status, timeout class, pagination defaults and limits,
  mutually exclusive or precedence-dependent parameters, side effects, and safe
  retry behavior.
- Clearly distinguish server behavior from SDK behavior. For example, describe
  tariffs, role access, geographic/IP restrictions, object ownership, and portal
  provisioning as server-side rules; describe validation, typed models, local rate
  limiting, retries, and re-authentication as SDK behavior.
- When a method has parameter precedence rules, document the winning parameter and
  the behavior when all optional selectors are absent. Do not reduce these rules to
  a bare type signature.
- For timestamps, state whether the field is local time, UTC, or a Unix timestamp
  exactly as defined by the contract. Do not normalize or label time zones without
  evidence.
- For billable or mutating operations, place the billing and side-effect warning
  immediately before the example, not only in a general overview page.
- For QR examples, document payment-code expiry, counter behavior, SMS confirmation,
  possible blocking, and the required recovery operation next to the relevant call.

## Verification commands

Install development dependencies with:

```bash
uv sync --extra dev
```

For Python changes, run:

```bash
uv run ruff check .
uv run black --check .
uv run mypy src
uv run pytest
```

For public API, model, contract, or documentation changes, also run the relevant
generators and strict documentation build:

```bash
uv run python scripts/generate_docs.py
uv run python scripts/verify_external_contract.py specifications/api-methods.yaml
uv run python scripts/verify_api_contract.py
uv run python scripts/build_docs_site.py
```

If a command is unavailable, requires external credentials, or cannot run in the
current sandbox, report that explicitly. Do not claim a check passed unless it was
actually executed successfully.

## Completion criteria

A task is complete only when:

- the requested behavior is implemented without unrelated changes;
- relevant tests cover the new or corrected behavior;
- applicable lint, formatting, type, contract, and documentation checks pass;
- public documentation matches the implementation;
- security and compatibility invariants remain intact;
- the final report lists changed files, checks run, and any remaining risks.

## Code review rules

During review, prioritize actionable correctness findings over style preferences.
Look specifically for:

- breaking changes to public Python or wire-format APIs;
- mismatches between service signatures, endpoint registry, models, and contracts;
- unsafe retries of mutating operations;
- operation budgets reset during retry or re-auth;
- session recovery deadlocks or concurrent-auth races;
- credentials or personal data entering logs, errors, telemetry, fixtures, or docs;
- blocking work in async paths;
- documentation examples that no longer match the public API.

For each finding, identify the concrete failure mode and the smallest safe fix. Do
not report purely hypothetical issues without a reachable scenario.
