    Совместимость со спецификацией API¶

    Этот документ фиксирует правила SDK, которые следуют из локальной спецификации API для корпоративных клиентов версии 1.1.60. Примеры ключей, идентификаторов сессий и паролей из исходного документа намеренно не переносятся в репозиторий.

    Договорные операции¶

    • contracts, limits, region_limits, restrictions и templates используют договор активной сессии, если contract_id не передан явно.
    • Явный contract_id всегда имеет приоритет, включая методы, где спецификация требует заголовок договора.
    • Денежные поля счёта и переводов принимаются как Decimal и сериализуются строкой.
    • productType, productGroup и regionlimit_id нормализуются через явные aliases request-моделей.
    • QR/MPC-функциональность сверена с отдельной спецификацией API QR версии 1.0.4 от 30.05.2024 и не относится к изменениям раздела 2B.

    Ответы и ошибки¶

    • Ответ рассматривается как конверт с status, data и timestamp.
    • SDK проверяет как HTTP-статус, так и status.code внутри тела ответа.
    • notAuthenticated запускает единственную повторную авторизацию и повтор запроса.
    • duplicateConflict считается ошибкой, а не сигналом для автоматического retry.

    Расхождения фактических ответов со спецификацией¶

    Модели ответов строятся по спецификации 1.1.60. Если API присылает другую форму, модель ослабляется точечно, а расхождение фиксируется здесь и в тестах tests/test_live_response_deviations.py (синтетические значения, реальная структура):

    Метод Поле Спецификация Фактический ответ Модель SDK
    get_transactions_v2, get_card_transactions_v2, get_transaction_detail data.result[].stor_transaction_id строка, обязательное null у несторнированных транзакций int | str | None
    get_azs_list_v2 data.result[].utc_timezone строка, обязательное null у части АЗС str | None
    get_card_detail data.result[].transaction_timeout.type число, обязательное буквенный код (H, D, M) или null, если таймаут не задан int | str | None
    get_dictionary data.result[].id тип не указан число в справочнике Services строка; число приводится к строке
    get_card_detail data.result[].card_auth_type строка, обязательное null, если тип аутентификации не задан str | None
    get_cards_v1 data.result[].can_work_offline, card_auth_type, date_expired обязательные поля могут отсутствовать необязательные, по умолчанию None
    get_users data.result[].contracts[].cards_count число, обязательное поле может отсутствовать у части договоров int | None, по умолчанию None
    set_restriction data[] строки ID ограничителей числами строки; число приводится к строке
    get_transaction_detail data.result[].date строка, обязательное поле не приходит str | None, по умолчанию None
    get_users data.result[].cards[].product, status строки, обязательные бывает null str | None
    get_transactions_v2, get_card_transactions_v2, get_transaction_detail data.result[].timestamp локальное время местное время со суффиксом Z datetime с часовым поясом UTC; используйте utc_time
    get_restrictions data.result[].date формат не указан; пример 09/03/2018 00:00:00 DD/MM/YYYY HH:MM:SS строка без разбора
    get_transactions_v2, get_card_transactions_v2, get_transaction_detail data.result[].id, check_id строки числа int | str
    get_card_transactions_v2, get_transaction_detail data.result[].price, sum, price_no_discount, sum_no_discount, discount, exchange_rate, qty строки (qty — uint); в get_transactions_v2 — float числа, в том числе дробные числа или строки
    get_invoices data.result[].amount, currency, date_end, last_update float / uint строки float | str, int | str
    get_users data.result[].cards[].available, contracts[].available строка bool bool | str
    get_users data.result[].date строка, обязательное null str | None
    get_card_drivers data.result[].role json строка str
    get_contract_data data.Is_dealer Is_dealer is_dealer принимаются оба имени
    get_reports data.result[].parameters[].label строка, обязательное бывает null str | None
    get_azs_list_v2 data.result[].id, siebel_id int строки str
    get_azs_list_v2 коды в adblue, services_with_card, services_without_card int строки int | str
    get_azs_list_v2 electric_charging_station, adblue, services_with_card, services_without_card объект [], если услуг нет пустой список приводится к None

    Если ответ всё же не совпадает с моделью, SDK выбрасывает ResponseValidationError (см. Ошибки и retry).

    Расхождения фактических запросов со спецификацией¶

    API принимает запросы, которые спецификация описывает иначе:

    Метод Параметр Спецификация Фактически SDK
    order_report_v1 email обязательный запрос без email принят, задача отчёта создана необязательный параметр
    get_info period YYYY-MM или YYYY-MM-DD принимает и YYYY-MM-DD HH:MM:SS: статистика за 24 часа от этого момента без period передаёт текущие дату и время
    update_template HTTP-метод PUT POST без _method=PUT отклоняется с кодом 405 по умолчанию POST с _method=PUT; use_post=False отправляет PUT
    update_template_limit тело запроса объект лимита массив отклоняется с кодом 405 отправляет объект; limits должен содержать ровно один лимит
    get_final_prices, check_purchase тело запроса JSON в форме goods не принимается как массив: 400 отправляет тело JSON
    create_user mobile строка только цифры, 11–13 знаков, без + передаёт значение как есть
    create_template, update_template name строка не длиннее 30 символов передаёт значение как есть
    set_card_group name строка от 1 до 50 символов; двоеточие в имени приводит к 500 передаёт значение как есть
    set_card_comment comment строка от 1 до 90 символов; пустая строка — 400, удалить комментарий нельзя передаёт значение как есть
    create_invite role строка принимаются Driver и Supervisor; другое значение — 400 «Некорректное значение.» без списка допустимых передаёт значение как есть

    Сервер не защищает от дублей: коды ошибок и надёжность повтора¶

    Часть операций, которые логично было бы считать защищёнными от дублирования (создание объекта с уже занятым именем или идентификатором, повторное удаление), не возвращают 409 duplicateConflict и код ошибки не всегда соответствует сути проблемы:

    Метод Действие Фактический ответ Что это значит
    create_user повтор с тем же mobile 403 accessDenied, «Указанный логин пользователя уже существует в системе» не 409; проверяйте текст сообщения, а не только код
    set_card_group создание с именем, которое уже занято 200, создаётся вторая группа с тем же именем уникальность имени сервер не проверяет — проверяйте список групп сами
    remove_card_group повторное удаление уже удалённой группы может прийти 403 accessDenied («Нет доступа») вместо 404 notFound не полагайтесь только на 404, чтобы отличить «уже удалено» от запрета доступа
    remove_card_group обычное удаление ответ обычно через 9–11 секунд; бывает, что ответа нет и через 90 секунд, а группа при этом удалена ошибка ожидания (httpx.ReadTimeout или OperationTimeoutError) не означает, что группа осталась: проверьте get_card_groups()
    set_card_comment два одинаковых запроса одновременно оба 200 защиты от параллельных дублей нет; для комментария это безопасно, для создающих методов — нет

    Из этого следуют практические выводы, отражённые в примерах методов выше: проверяйте состояние самостоятельным чтением до повторной отправки изменяющего запроса, а не по коду ошибки.

    Правила сервера, которых нет в спецификации¶

    Метод Наблюдение Что учесть
    resend_invite Повторная отправка раньше чем через минуту после предыдущей, в том числе сразу после create_invite(with_send=True), отклоняется ответом 429 «С момента последней попытки отправки должна пройти 1 минута». После одной успешной повторной отправки attempts («количество попыток повторных отправок в день») изменился с 2 на 0, expired_at не изменился 429 здесь означает паузу приглашения, а не общий лимит частоты; повторная отправка срок не продлевает
    prolong_invite prolong_invite(with_send=False) отвечает data: true, но expired_at и attempts в get_invites() не меняются после продления проверьте expired_at в get_invites(), а не полагайтесь на true
    set_cards_to_group После data: true около 15 секунд у группы status и cards_count пустые, у карты нет group_id; примерно через 30 секунд группа синхронизирована не считайте привязку неудавшейся по первому чтению; повторите чтение через 30–60 секунд
    attach_card Сразу после привязки у карты пользователя carrier = null, у договора нет cards_count; примерно через 90 секунд поля заполнены читайте get_users() для проверки привязки не раньше чем через пару минут
    order_invoice Заказ счёта отвечает data: true; заказанный счёт появляется в get_invoices с задержкой — через 5 секунд после заказа его ещё не было пустой список сразу после заказа не означает неудачу; перед повторным заказом подождите и проверьте get_invoices снова
    get_report_job_list_v1 Задача появляется сразу после order_report_v1; available_after уменьшается как обратный отсчёт в секундах; отчёт за месяц был готов примерно через 5 минут, что согласуется с заявленными ~300 секундами скачивайте файл, когда available_after станет 0

    Форматы дат различаются между методами¶

    Спецификация описывает большинство дат как строки без формата, а API использует разный порядок дня и месяца. SDK отдаёт такие поля строкой без разбора, поэтому формат выбирает приложение:

    Методы Поле Формат
    get_restrictions date DD/MM/YYYY HH:MM:SS — день первым
    get_limits, get_region_limits date MM/DD/YYYY HH:MM:SS — месяц первым
    get_users date (дата рождения) MM/DD/YYYY, бывает null
    get_card_drivers, get_azs_list_v1, get_azs_list_v2 поля дат MM/DD/YYYY … — месяц первым
    get_transactions_v2, get_card_transactions_v2, get_transaction_detail timestamp, utc_time ISO 8601; timestamp — местное время, хотя оканчивается на Z; время UTC — в utc_time

    При дне меньше 13 ошибка формата не проявляется: строка 03/04/2026 разберётся и как 3 апреля, и как 4 марта. Разбирайте даты каждого метода своим форматом из таблицы, например datetime.strptime(value, "%d/%m/%Y %H:%M:%S") для ограничителей и "%m/%d/%Y %H:%M:%S" для лимитов.

    Код ответа не всегда указывает причину¶

    Часть ошибок приходит с кодом, который по спецификации означает другое. Решение по такому ответу принимайте по тексту сообщения (exc.server_messages), а не только по классу исключения:

    Ответ Методы Фактическая причина
    403 accessDenied get_final_prices, check_purchase отказ процессинга; код причины только в тексте: «ОТКАЗ. Недостаточно средств. [Код ошибки: 51]», «… [Код ошибки: 05]», «… [Код ошибки: 12]». Для одной карты и точки два метода могут вернуть разные коды
    403 accessDenied create_user логин (телефон) уже существует
    403 accessDenied detach_card карта не была привязана к пользователю
    403 accessDenied remove_card_group группа уже удалена
    403 с HTML вместо JSON DEMO, любые методы запрос заблокирован сетевым фильтром (см. DEMO)
    500 internalError create_invite приглашение без карт и шаблона: «Приглашение не готово к отправке»
    500 internalError set_card_group двоеточие в имени группы
    429 resend_invite пауза в одну минуту между отправками приглашения, а не лимит частоты

    Два практических вывода:

    • AccessDeniedError не всегда означает проблему с ролью, ключом или IP;
    • ServerError не всегда временный сбой: на ошибки данных из таблицы повтор того же запроса не поможет, нужно исправить запрос.

    Тарификация чтения¶

    Счётчик запросов в get_info() подтверждает тарификацию из каталога методов: чтение ограничителей (get_restrictions) и региональных лимитов (get_region_limits) тарифицируется, а чтение продуктовых лимитов (get_limits) и статистики (get_info) — нет. Поэтому автоматические повторы платных методов чтения тоже расходуют запросы. Тарификацию каждого метода смотрите в своде методов API.

    Поля ответа, которых нет в спецификации¶

    API присылает поля, отсутствующие в таблицах «Параметры ответа», например productTypeName и w4_id в лимитах (get_limits), accepted_at в приглашениях (get_invites), full_address в get_azs_list_v1. Модели ответов SDK такие поля не отбрасывают: они доступны через model.model_extra. Спецификация их не описывает, поэтому опирайтесь на них осторожно — они могут измениться без предупреждения.

    DEMO: успешный ответ без выполнения операции¶

    DEMO-стенд проверяет формат запроса и отвечает одним из двух ответов: запрос верен или ошибка. Для части изменяющих методов успешный ответ на DEMO не означает, что операция выполнена:

    Метод Ответ на DEMO Фактический эффект
    move_to_card, move_to_contract data: true остаток кошелька не меняется
    order_report data: {"job_id": []} задача отчёта не создаётся
    set_card_product data — список карт продукт карты меняется сразу и виден в get_cards_v2
    block_card data — список карт статус карты меняется сразу

    Поэтому DEMO подходит для проверки формы запросов и ответов, но не для проверки денежных операций и формирования отчётов.

    Другие особенности DEMO:

    • Состояние общее и сохраняется. Блокировка карты и смена продукта остаются в силе между запросами, а стенд общий для всех клиентов. Не рассчитывайте на исходное состояние данных и возвращайте изменения после проверки.
    • get_transactions_v2 отвечает HTTP 405 при status.code 200. Данные в ответе есть, но SDK проверяет HTTP-статус и поднимает APIError с кодом 405. При любом периоде возвращается один и тот же набор старых транзакций без product_name и utc_time. Проверяйте этот метод вне DEMO.
    • Сетевой фильтр блокирует некоторые User-Agent. Запрос с заголовком User-Agent: python-httpx/… получает 403 с HTML-страницей вместо JSON. SDK отправляет собственный User-Agent: apisdkopti24, поэтому его запросы это не затрагивает; ответ касается сторонних скриптов и инструментов с заголовком по умолчанию. В SDK такой ответ стал бы AccessDeniedError без сообщения сервера.

    Повтор запросов¶

    • Безопасные операции чтения могут повторяться после временной сетевой ошибки.
    • Операции изменения данных не повторяются после неопределённого сетевого сбоя.
    • Авторизационные запросы разнесены минимум на 5 секунд.
    • Ответы 429 и 509 повторяются только для безопасных операций.

    Такой подход намеренно строже обычного retry по HTTP-методу: он исключает повторную отправку создания, оплаты или другого изменения с неизвестным результатом первого запроса.

    Ограничение частоты¶

    Спецификация задаёт 2 запроса в секунду для DEMO и 5 запросов в секунду для рабочей среды. Упреждающий лимит включён по умолчанию; переопределить частоту можно через переменную окружения или RateLimitPolicy в настройках клиента (подробнее — в разделе «Ограничьте частоту и параллельность запросов»):

    API_REQUESTS_PER_SECOND=2

    Лимитер общий для экземпляра transport и синхронизирован между конкурентными корутинами.

    Фактическая частота без 509¶

    Заявленный лимит на практике недостижим: сервер отвечает 509 «Превышен лимит запросов» задолго до 5 запросов в секунду. При последовательных запросах строго по расписанию:

    Частота Доля ответов 509
    1 запрос в секунду не было
    2 запроса в секунду около трети
    4 запроса в секунду около 30 %
    около 2 запросов в секунду на DEMO около пятой части

    509 приходит и тогда, когда за предыдущую секунду сервер принял всего 0–2 запроса, поэтому алгоритм ограничения не сводится к счётчику за календарную секунду.

    Что из этого следует для SDK:

    • Значение SDK по умолчанию (5 запросов/с) соответствует спецификации, а не фактическому поведению. Для устойчивого потока задайте API_REQUESTS_PER_SECOND=1 (см. «Ограничьте частоту и параллельность запросов»).
    • Чтение SDK после 509 повторяет с паузой, поэтому при большей частоте чтение всё равно завершится, но медленнее и с лишними попытками.
    • Изменяющие операции после 509 не повторяются: неизвестно, выполнил ли сервер такой запрос. При частоте выше 1 запроса в секунду заметная часть переводов, блокировок и созданий завершится RateLimitError; после неё проверьте состояние чтением, прежде чем отправлять операцию снова.
    • По спецификации тарифицируются только ответы с HTTP 200; тарифицируется ли ответ 509, в спецификации не описано.

    Альтернативный HTTP-метод¶

    Для методов, где инфраструктура не пропускает PUT или DELETE, SDK поддерживает POST с _method=PUT или _method=DELETE. Параметр use_post доступен в операциях пользователей, приглашений и шаблонов. Исходный payload копируется и не изменяется.

    Registry¶

    Registry содержит OperationSpec, объединяющий response type, HTTP-маршрут, версию API, demo-доступность, timeout, idempotency и класс retry. Каталог собирается из экспортированных спецификаций доменных модулей без AST-разбора.

    Независимый контракт, однократно преобразованный из свода методов, находится в specifications/api-methods.yaml. Команда python scripts/verify_external_contract.py specifications/api-methods.yaml строго сверяет external_code, operation, route name, HTTP-метод, версию, путь, DEMO-доступность и тарификацию с registry. Исходный Excel остаётся вне репозитория. Для calculate_prices и check_purchase в YAML явно зафиксировано расхождение: сводная таблица указывает GET, но наличие request body в детальной спецификации требует POST.

    Расширенный контракт specifications/api-contract-v1.1.60.yaml однократно сформирован из DOCX-спецификации 1.1.60. Он дополнительно фиксирует параметры и типы запросов, обязательность полей, aliases request-моделей, response schemas и санитизированные официальные примеры. Исходный DOCX и секреты из примеров в репозитории не хранятся. CI сверяет этот контракт с OperationSpec, публичными сигнатурами сервисов и Pydantic schemas.

    Для QR/MPC-операций MPC, pay, initMPC, confirmMPC, updateMPC, deleteMPC и resetMPC используется отдельный первичный источник — спецификация сервиса API QR версии 1.0.4. Из неё взяты обязательность параметров, ограничения PIN и устройства, структура списка МПК и ответ генерации платёжной строки. Секреты и действующие идентификаторы из примеров источника в репозиторий не переносятся.

    Границы ответственности¶

    Географические ограничения, срок жизни сессии и серверные квоты контролируются API. SDK не пытается обходить эти ограничения, а только нормализует ошибки и снижает вероятность лишних запросов.
